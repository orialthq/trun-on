# Product Definition

**상태:** Draft · Input-to-Organization Baseline

**플랫폼:** Android first

**제품 영역:** Skincare content organization

## 0. 문서 읽는 법

이 문서는 6주 베이스라인의 **목표 제품 계약**입니다. 현재 실행 가능한
pre-alpha는 그 계약의 첫 수직 흐름이며 다음 범위까지 구현되어 있습니다.

- Android URL·텍스트 수신과 versioned 로컬 snapshot
- 규칙 기반 단일 제품 후보, 일부 주제와 명시적 광고 표시 추출
- 공유 텍스트의 진술 근거 인용
- 브랜드·제품명·카테고리·용량 확인·수정
- 사용자 확인을 거친 완전 일치 제품의 제품별 정리

현재는 다제품 추출, 스크린샷·OCR, 제품 필드 근거 탐색, 비동기 분석,
수동 병합·분리, 진술 편집, 삭제·되돌리기, 내용 기반 중복 제거를
지원하지 않습니다. 아래 요구사항에서 이 항목들은 현재 동작을
설명하는 것이 아니라 베이스라인 완료 조건을 정의합니다.

## 1. 한 문장 정의

SNS에서 발견한 스킨케어 콘텐츠를 공유하면 원본을 보존하고,
제품·주장·맥락을 근거와 함께 분석해 같은 제품별로 정리하며, 불확실한
결과는 사용자가 확인하고 수정할 수 있게 한다.

## 2. 이번 단계의 목표

장기 비전은 저장한 정보를 실제 행동으로 연결하는 것이지만, 현재
단계에서는 활용이나 구매 의사결정을 구현하지 않습니다.

> 사용자가 공유한 콘텐츠를 신뢰할 수 있는 구조화 기록으로 바꾸는 것

이번 단계가 답해야 하는 질문은 다음과 같습니다.

1. 사용자가 무엇을 공유했는가?
2. 콘텐츠 안에 어떤 제품이 언급됐는가?
3. 콘텐츠는 각 제품에 관해 무엇을 말했는가?
4. 분석 결과는 원본의 어느 부분에서 나왔는가?
5. 같은 제품을 다룬 콘텐츠가 올바르게 묶였는가?
6. 무엇이 확실하고 무엇을 사용자가 확인해야 하는가?

`무엇을 사야 하는가`, `나에게 맞는가`, `언제 사야 하는가`는 다음
단계의 질문입니다.

## 3. 해결할 문제

사용자는 여러 SNS에서 뷰티 콘텐츠를 저장하지만 정보가 플랫폼별
저장함에 흩어집니다. 다시 찾더라도 다음 작업을 수동으로 반복합니다.

- 콘텐츠에서 정확한 브랜드와 제품을 다시 식별한다.
- 같은 제품에 관한 여러 콘텐츠를 다시 모은다.
- 제품 정보, 작성자의 주장, 사용 경험을 구분한다.
- 광고·협찬 표시가 실제로 있었는지 원문을 다시 확인한다.
- 기억이 아닌 원본을 기준으로 내용을 재정리한다.

단순히 링크를 한곳에 모으는 것만으로는 이 문제가 해결되지 않습니다.
반대로 너무 빨리 추천과 구매 결정으로 넘어가면 잘못된 제품 식별과
근거 없는 요약 위에 결과가 쌓입니다.

## 4. 첫 사용자

연령보다 행동으로 정의합니다.

- 인스타그램·유튜브·틱톡 등에서 뷰티 콘텐츠를 주 5개 이상 저장한다.
- 같은 제품을 여러 크리에이터의 콘텐츠에서 반복해서 본다.
- 저장한 콘텐츠를 다시 찾고 내용을 비교하는 데 시간을 쓴다.
- 광고성 표현과 실제 사용 경험을 원문 기준으로 구분하고 싶어 한다.
- AI 자동 정리는 원하지만 잘못된 결과를 직접 고칠 수 있기를 원한다.

## 5. 핵심 Job to be Done

> SNS에서 관심 있는 스킨케어 콘텐츠를 발견했을 때, 원본을 잃지 않고
> 어떤 제품과 내용인지 자동으로 정리하되 애매한 부분은 내가 빠르게
> 바로잡고 싶다.

## 6. 목표 제품 흐름

1. 사용자가 SNS, 브라우저 또는 앱 안에서 콘텐츠를 공유한다.
2. 앱은 분석보다 먼저 원본과 수집 시점을 보존한다.
3. 앱은 분석 가능 자료가 충분한지 판단한다.
4. 제품 언급, 콘텐츠의 주장, 사용 맥락, 명시적 광고 표시를 추출한다.
5. 각 결과에 원본 근거와 불확실성을 연결한다.
6. 제품 식별이나 묶음이 애매하면 확인 필요 상태로 둔다.
7. 사용자는 후보를 확인·수정하고 잘못된 묶음을 분리하거나 합친다.
8. 확인된 콘텐츠는 콘텐츠 보관함과 제품 보관함에 정리된다.

분석 실패가 저장 실패가 되어서는 안 됩니다. 접근이 제한된 URL,
지원하지 않는 자료, 일시적 분석 오류를 서로 다른 상태로 보여줘야
합니다.

## 7. 목표 입력 계약

한 번의 공유는 하나의 `RawCapture`입니다. 원본은 파생 분석 결과와
분리하고, 사용자가 삭제하기 전까지 덮어쓰지 않습니다.

### 7.1 지원 입력

| 입력 | 우선순위 | 처리 원칙 |
|---|---|---|
| Android 공유 URL·텍스트 | P0 | 즉시 로컬 보존 후 비동기 분석 |
| 앱 안에서 붙여넣은 URL·텍스트 | P0 | 공유 입력과 같은 계약 사용 |
| 스크린샷 1~5장 | P0.5 | 안전한 앱 전용 복사와 OCR 구현 후 지원 |
| 사용자의 선택적 메모 | P0 | 콘텐츠 원문과 별도 필드로 저장 |
| SNS 저장 목록 자동 가져오기 | 비범위 | 플랫폼 제한을 우회하지 않음 |

### 7.2 RawCapture 필드

- 고유 ID와 수집 시각
- 출처 앱 패키지와 추정 플랫폼
- 입력 종류: `sharedText`, `url`, `image`, `pastedText`, `mixed`
- 원본 텍스트와 원본 URL
- 정규화된 URL
- 첨부 파일의 MIME 형식, 크기, 로컬 참조
- 중복 수신·재시도를 판별할 payload hash
- 콘텐츠와 분리된 사용자 메모
- 입력 계약 버전
- 보존·삭제 상태

### 7.3 입력 정책

- 텍스트 또는 이미지처럼 실제 내용을 담은 자료가 있어야 완전 분석을
  보장할 수 있습니다.
- URL만 공유해도 원본 저장은 성공합니다.
- 접근할 수 없는 URL은 `자료 부족`으로 표시하고 텍스트 또는 스크린샷
  추가를 요청합니다.
- 원본 URL과 정규화된 URL을 모두 보존합니다.
- 하나의 콘텐츠에 여러 제품이 등장할 수 있습니다.
- 접근 권한이 없는 원문을 우회해서 가져오거나 영상을 다운로드하지
  않습니다.

## 8. 목표 처리 상태

상태는 수집, 자료 준비, 분석, 사용자 확인, 정리를 구분합니다.

```text
received
├── material_ready → analyzing → analyzed → organized
│                                  └── needs_review → organized
├── source_limited
├── failed_retryable
├── unsupported
└── deleted
```

| 상태 | 의미 |
|---|---|
| `received` | 원본 수신과 보존이 완료됨 |
| `material_ready` | 분석할 텍스트 또는 이미지가 준비됨 |
| `source_limited` | URL은 있지만 분석할 본문을 확보하지 못함 |
| `analyzing` | 구조화 분석 진행 중 |
| `analyzed` | 유효한 구조화 결과가 생성되어 정리 여부를 판정 중 |
| `needs_review` | 핵심 필드 또는 제품 묶음에 사용자 확인이 필요함 |
| `organized` | 분석 결과가 보관함에 반영됨 |
| `failed_retryable` | 일시적 오류이며 원본으로 재시도 가능함 |
| `unsupported` | 현재 지원하지 않는 형식임 |
| `deleted` | 사용자 요청으로 원본과 파생 데이터가 삭제됨 |

## 9. 분석 계약

분석 결과는 콘텐츠, 제품 언급, 콘텐츠 진술의 세 층으로 나눕니다.

### 9.1 SourceDocument

콘텐츠 자체에서 실제로 확인된 정보입니다.

- 플랫폼과 콘텐츠 형식
- 제목, 본문, OCR 텍스트
- 작성자와 게시 시각
- 언어
- 자료 완전성: `complete`, `partial`, `linkOnly`
- 명시적 광고·협찬 표시 상태
- 분석에 사용한 입력 자료 목록

원본에서 확인하지 못한 작성자나 게시 시각을 추측해서 채우지 않습니다.

### 9.2 ProductMention

콘텐츠 안에서 발견한 개별 제품 언급입니다.

- 원문에 나온 브랜드명과 제품명
- 카테고리
- 라인, 옵션, 용량 또는 규격
- canonical product 후보와 대안 후보
- 식별 상태: `exact`, `likely`, `ambiguous`, `unresolved`
- 각 필드의 근거와 불확실성

`ProductMention`과 `CanonicalProduct`는 별개입니다. 언급이 확인됐더라도
정확한 제품을 특정하지 못할 수 있습니다.

### 9.3 Statement

콘텐츠가 제품에 관해 말한 내용을 원본 단위로 기록합니다.

- 원문 excerpt 또는 OCR span
- 연결된 제품 언급
- 유형: 제품 정보, 작성자 주장, 사용 경험, 사용법, 단점·주의 표현,
  비교 언급, 광고 표시
- 정규화된 주제: 보습, 진정, 사용감, 향, 밀림, 백탁, 자극 언급 등
- 콘텐츠에 명시된 사용 기간, 피부 타입, 사용 순서 등의 맥락
- 명확한 경우에만 방향: 긍정, 부정, 혼합, 중립
- 원본 근거

`진정 효과가 있다`가 아니라 `이 콘텐츠에서 진정에 도움이 됐다고
언급함`으로 표현합니다. 외부 제품 데이터로 검증하기 전 성분명도
`언급된 성분`입니다.

## 10. 근거와 불확실성 계약

제품 식별과 분석 필드는 최소한 다음 메타데이터를 가집니다.

- 값
- 상태: `extracted`, `inferred`, `userConfirmed`, `userCorrected`,
  `unknown`
- 내부 평가용 confidence score
- UI용 confidence band: `높음`, `확인 권장`, `확인 필요`
- 하나 이상의 `EvidenceRef`
- 대안 후보
- 결과를 만든 analysis run ID

`EvidenceRef`에는 다음이 포함됩니다.

- 근거 종류: 공유 텍스트, 스크린샷 OCR, 접근 가능한 페이지 메타데이터,
  사용자 메모
- 정확한 텍스트 범위 또는 이미지 번호와 영역
- 캡처 시점
- 원본을 다시 여는 참조

요약 문장과 핵심 태그에는 반드시 근거가 있어야 합니다. 근거가 없는
분석 문장은 사용자에게 보여주지 않습니다. 모델·프롬프트·스키마 버전과
분석 시점을 기록해 재분석 결과를 추적합니다.

## 11. 제품 병합 가드레일

잘못된 자동 병합은 여러 출처의 주장을 엉뚱한 제품에 연결하므로 가장
위험한 정리 오류입니다.

- 브랜드, 제품명, 라인·옵션 식별이 충분할 때만 자동 병합합니다.
- 애매한 후보는 기존 제품에 넣지 않고 `제품 후보`로 둡니다.
- 자동 병합보다 병합 제안을 우선합니다.
- 변형 제품, 용량, 리뉴얼 여부를 확인하지 못하면 별도 묶음으로 둡니다.
- 사용자는 언제든 묶음을 분리하고 같은 제품 묶음을 합칠 수 있습니다.
- 병합·분리 이력과 그 근거를 기록합니다.

원칙은 **잘못 합치는 것보다 덜 합치는 것이 낫다**입니다.

## 12. 사용자 확인과 수정

모든 결과를 매번 확인시키지 않고 정리를 망칠 수 있는 핵심 항목만 확인
큐에 올립니다.

사용자는 다음 작업을 할 수 있어야 합니다.

- 브랜드, 제품명, 옵션, 용량 편집
- 여러 제품 후보 중 선택
- `제품을 특정할 수 없음` 선택
- 콘텐츠 안의 제품 추가·삭제
- 잘못 묶인 제품 분리
- 같은 제품으로 확인한 묶음 합치기
- 잘못 추출된 진술 삭제 또는 유형·태그 수정
- 원본을 유지한 채 재분석
- 원본과 파생 결과 삭제
- 자신의 수정 되돌리기

수정은 원본을 덮어쓰지 않습니다. 원래 값, 수정 값, 수정 주체, 시각을
`Correction` 이벤트로 남기고 파생된 보관함만 다시 계산합니다.

## 13. 정리 결과 계약

### 13.1 콘텐츠 보관함

- 플랫폼, 수집 시각, 원본 미리보기
- 분석 가능한 자료의 완전성
- 추출된 제품과 주제
- 분석 상태와 확인 필요 항목 수
- 원본 열기, 재분석, 삭제
- 플랫폼, 날짜, 카테고리, 상태 필터와 검색

### 13.2 제품 보관함

- 확인된 canonical product 또는 미확정 제품 후보
- 제품이 등장한 콘텐츠 수
- 제품 기본 식별 정보
- 반복 언급된 주제와 출처 수
- 출처별로 묶은 콘텐츠의 진술
- 명시적 광고·협찬 표시 상태
- 원본 근거 열기
- 제품 묶음 합치기와 분리하기

예:

```text
가벼운 사용감 · 3개 콘텐츠에서 언급
밀림이 있었다 · 1개 콘텐츠에서 언급
협찬 표시 확인 · 2개
캡처 자료에서 표시 미발견 · 1개
```

반복 언급 횟수는 정리 정보이지 제품 신뢰도나 추천 점수가 아닙니다.

## 14. 베이스라인 요구사항

| ID | 우선순위 | 요구사항 |

## 15. AI와 정보 표현 원칙

- 제품 매칭이 불확실하면 추측해 확정하지 않습니다.
- 콘텐츠의 주장은 `콘텐츠에서 언급됨`으로 표시합니다.
- 광고 여부를 임의 추론하지 않고 명시적 표시만 전달합니다.
- `표시 미발견`을 `광고 아님`으로 바꾸지 않습니다.
- 요약에서 원본보다 강한 효능 표현을 만들지 않습니다.
- 사용자 메모와 콘텐츠의 주장을 서로 다른 출처로 표시합니다.
- 근거 없는 요약은 저장하거나 노출하지 않습니다.
- 동의 없이 공유 원본을 별도의 모델 학습 데이터로 재사용하지 않습니다.

## 16. 성공 지표

### 북극성 지표: 24h Correctly Organized Rate

```text
24시간 안에 올바른 제품·출처 묶음으로 정리된 지원 입력 수
÷ 유효한 지원 입력 수
```

초기에는 사용자의 확인 결과 또는 표본 수동 감사를 정답으로 사용합니다.
접근 제한으로 자료가 부족한 URL은 모델 분석 실패와 분리해서 측정합니다.

### 초기 베타 가설 목표

100~200개의 라벨링된 실제 입력으로 기준선을 만든 뒤 목표를 조정합니다.

- 입력 수신·원본 보존 성공률 99% 이상
- 지원 입력의 24시간 내 정리 완료율 80% 이상
- 사용자 1회 확인 후 정확한 제품 식별률 90% 이상
- 잘못된 자동 병합률 2% 이하
- 사용자에게 노출된 진술의 근거 연결률 100%
- 표본 감사에서 원본에 없는 주장 생성 0건
- 중복 Capture 생성률 1% 이하
- 확인 필요 항목의 중앙 수정 시간 30초 이하
- 입력 10개의 공유부터 정리 완료까지 중앙 시간 5분 이하
- 삭제 성공률 100%, 원본 유실 0건

### 퍼널

```text
received
→ material_ready 또는 source_limited
→ analyzed
→ needs_review
→ organized
```

수집 성공률, 분석 가능률, 사용자 수정률, 자동 병합 정밀도, 처리 시간,
삭제 성공률을 각각 측정합니다.

## 17. 완료 조건

> 실제 Android 기기에서 서로 다른 플랫폼의 스킨케어 콘텐츠 10개를
> 공유한다. 입력에는 URL·텍스트·스크린샷, 여러 제품이 등장하는 사례,
> 제품 식별이 불명확한 사례가 포함된다.

완료 시 다음이 모두 성립해야 합니다.

- 원본이 하나도 유실되지 않는다.
- 각 입력의 처리 상태를 이해할 수 있다.
- 제품·진술·명시적 광고 표시가 근거와 함께 정리된다.
- 불확실한 값은 자동 확정되지 않고 확인 필요로 남는다.
- 사용자가 결과를 수정하고 제품 묶음을 합치거나 분리할 수 있다.
- 원본과 분석 결과를 삭제할 수 있다.
- 제품 보관함의 모든 집계에서 원본 출처로 이동할 수 있다.
- 구매 추천, 제품 우열, 개인 적합성 판단이 노출되지 않는다.
